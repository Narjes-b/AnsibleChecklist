# v0.0.7 audit, reproduction, and fixes (2026-10-15)

This is the entry point for the state of the v0.0.7 study after the
2026-10-15 audit. It records what was broken, how the frozen run was
reproduced, and what was fixed. Fixes are listed in `CHANGELOG.md` under
*Unreleased*.

## 2. Reproduction of the frozen run

The frozen run was re-executed on 2026-10-15 from the analysis commit
`d1711f90` in a separate worktree, with the canonical runner (four repository
jobs, recorded test pass: 1,031 passed, 2 skipped) and the same ansible-lint
26.4.0. Before the run, the 124 checkouts that the parent-fetch script had
deepened were returned to their frozen shallow state (target SHA re-added to
`.git/shallow`, promisor configuration removed; backups kept), and the five
checkouts left dirty by the frozen run itself were reset. Afterwards, 27
checkouts resolve `HEAD^`, as before the fetch script ran.

| Measure | Frozen run | Reproduction |
|---|---:|---:|
| Repositories completed / timed out | 206 / 1 | 206 / 1 |
| Raw findings | 390,286 | 390,286 |
| Canonical occurrences | 376,115 | 376,114 |
| Internal static-source occurrences | 265,434 | 265,434 |
| Review-range occurrences | 497 | 497 |
| GitLeaks occurrences | 1,434 | 1,434 |

Every AnsibleGuard internal, review, and GitLeaks occurrence reproduced
exactly. Seven ansible-lint occurrences in two repositories differ (four only
in the frozen run, three only in the reproduction):

- `redhat-ci[no-role-prefix]` messages embed a Python set whose element order
  changes between processes; the message is part of the fingerprint, so the
  occurrence ID changed. **Fixed:** set literals in ansible-lint messages are
  normalized to sorted order before any fingerprint is computed.
- The same ansible-lint finding was attributed to a different file of the same
  role between runs, and `warning[outdated-tag]` notices come from
  ansible-lint's transform pass. Both are provider behaviour; the transform
  pass can no longer write to the checkout (workspace guard).

The reproduction run itself stamped tool commit `15ff61b9` instead of
`d1711f90` on every repository, because the editable installation resolves
AnsibleGuard from the main checkout. The validation gate therefore refused
publication (all 207 rows `failed` on provenance) although the analyzed source
was byte-identical; the comparison above uses `aggregate()` directly and is an
analysis check, not a publishable run. A publishable regeneration needs the
analysis package installed from the analysis commit itself (or `PYTHONPATH`
set to that checkout's `src/` together with `--skip-tests` after a recorded
clean test run) and about 9 GB free disk.

The reproduction also showed that the frozen run mutated exactly the same five
checkouts again (`jon77p/infrastructure`: three YAML files rewritten by
ansible-lint; `osism/*`, `UtrechtUniversity/yoda`: `.ansible/` caches;
`stackhpc/ansible-slurm-appliance`: `__pycache__` from imported repository
plugins). With the workspace guard, all five stay clean (verified on the real
checkouts: three files restored byte-for-byte, caches removed, pre-existing
ignored content kept).


## 3. Consequences for the human-validation phase

- The frozen agreement pilot (`study/validation-v007-human/`) is unchanged
  and remains valid as a record. Its review/history family was built from
  findings produced by the shallow-range fallback; with the detector fix most
  of those diff-dependent findings would not be emitted. Regenerate the
  review/history family (and the truncated structure/reuse bundles) as a new
  pilot version before labels are collected.
- Parents for diff-dependent calibration candidates must come from the side
  repositories created by the redesigned fetch script, never from the frozen
  checkouts.
- Any precision or prevalence statement for the review rules must use a run
  produced with the fixed detector; the frozen run's review counts describe the
  fallback artifact.
